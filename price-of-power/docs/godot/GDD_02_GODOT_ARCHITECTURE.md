# Цена власти — GDD 0.1: архитектура Godot 4

## 1. Технологии

- Godot 4.x;
- типизированный GDScript;
- Windows 10/11 — первая платформа;
- Python — внешние симуляции, проверки данных, балансировка и редакторские инструменты;
- Git — исходники и текстовые данные;
- временные 3D-ассеты подключаются через заменяемые сцены.

Чистый Python не используется как игровой движок. Это позволило бы применять знакомый язык, но потребовало бы самостоятельно строить редактор, 3D-сцены, навигацию, освещение, интерфейс и экспорт.

## 2. Принципы архитектуры

1. Симуляция не зависит от визуальных сцен.
2. Состояние изменяется только через команды и системные процессы.
3. UI читает публичное представление, а не скрытые данные.
4. Визуальный объект можно заменить без изменения идентификаторов и сохранений.
5. Любое случайное решение воспроизводимо из seed и журнала команд.
6. Сохранение содержит данные, а не ссылки на активные узлы сцены.
7. Сюжетные сцены подписываются на факты мира, а не управляют экономикой напрямую.

## 4. Автозагрузки

Минимальный набор глобальных служб:

- `AppState`: текущий режим и ссылка на загруженное состояние;
- `SceneRouter`: переходы и затемнение;
- `SaveService`: сохранение, загрузка и миграции;
- `AudioService`: пока без контента, но с готовыми шинами;
- `DataRegistry`: проверенные определения сущностей.

Симуляционные системы не должны становиться глобальными синглтонами без необходимости. Они создаются владельцем кампании и получают состояние явно.

## 5. Сцены верхнего уровня

```text
AppRoot
├── WorldViewport
├── PresentationLayer
├── HudLayer
├── ModalLayer
└── TransitionLayer
```

Режимы:

- главное меню;
- карта региона;
- карта столицы;
- замок;
- диалог;
- стратегическое планирование;
- выполнение периода;
- бой;
- эпилог.

## 6. Карты

### Карта региона

- 3D-рельеф средней детализации;
- камера с панорамированием, вращением и ограниченным масштабированием;
- дороги представлены графом маршрутов;
- армии, обозы и представители следуют по рёбрам графа;
- города и области являются интерактивными сценами-прокси;
- дальние государства используют упрощённые визуальные представления.

### Столица

- отдельная 3D-сцена;
- подготовленные строительные площадки;
- здания являются экземплярами `BuildingView` со стабильным `building_id`;
- состояние симуляции определяет вариант модели, активность NPC и эффекты;
- клики обрабатываются через выбор объекта в мире, а не HTML-подобные панели.

### Замок

- один визуальный комплекс;
- пять постановочных зон;
- переходы управляются камерой и `SceneRouter`;
- диалоговый слой не уничтожает 3D-сцену помещения.

## 7. Бой

Бой использует отдельное состояние `BattleState`, созданное из состояния кампании. После завершения результат применяется к кампании одной проверяемой командой.

Основные компоненты:

- `BattleController`;
- `TacticalPauseController`;
- `UnitController`;
- `FormationController`;
- `OrderQueue`;
- `MoraleModel`;
- `SiegeSection`;
- `BattleCamera`;
- `BattleReport`.

Каждый отряд является логической единицей. Отдельные визуальные бойцы отображают состав, потери и строй, но не обязаны быть полноценными автономными агентами. Это позволяет показывать сотни людей без дорогого индивидуального ИИ.

Навигация делится на зоны и коридоры. Стены, ворота и лестницы создают специальные переходы. Динамический пролом обновляет локальный навигационный участок, а не перестраивает всю карту.

## 8. Диалоги

Диалог хранится как данные:

- условия появления;
- известные игроку темы;
- реплики;
- запросы уточнения;
- варианты действия;
- необязательный тон;
- команды симуляции;
- наблюдаемый итог;
- идентификаторы будущей озвучки.

Текст не должен напрямую менять ресурсы. Вариант диалога формирует команду, которую валидирует симуляция.

## 9. Сохранения

- свободные ручные сохранения вне активной боевой анимации;
- автосохранение перед выполнением периода, перед боем и после его результата;
- версия схемы данных;
- миграции старых сохранений;
- журнал последних команд для диагностики;
- seed и состояние генераторов случайности;
- снимок симуляции без временных визуальных узлов.

## 10. Замена ассетов

Каждый визуальный объект подключается через оболочку:

```text
BuildingView
├── PlaceholderModel или ProductionModel
├── InteractionArea
├── StateEffects
└── AnchorPoints
```

Внешняя сцена сохраняет контракт, поэтому модель, материалы и анимации можно заменить позднее. Аналогичный принцип применяется к портретам, бойцам, интерфейсным темам и звукам.

## 11. Тестирование

### GDScript

- команды не мутируют состояние при ошибке;
- воспроизводимость seed;
- сохранение и загрузка;
- экономика и население сохраняют инварианты;
- делегирование использует данные назначенного человека;
- сведения не раскрывают скрытое состояние;
- результат боя согласован с потерями.

### Python

- массовые прогоны кампании;
- анализ экономики;
- поиск недостижимых событий;
- проверка ссылок и идентификаторов;
- статистика развязок;
- обнаружение необратимых спиралей поражения.

## 12. Производительность

- целевая платформа: средний игровой ПК;
- логическая частота симуляции отделена от кадров;
- визуальные толпы используют уровни детализации;
- дальние бойцы анимируются группами;
- карта региона не симулирует каждого жителя;
- городские потоки являются агрегированными визуальными представителями населения.
